# Coordinated writing in Hermes Helmet: a retrospective Blueprint

Hermes Helmet is an open-source software factory from [Machine Wisdom AI](https://machine-wisdom.ai/). This Blueprint describes how it already coordinates a document that several Hermes workers write together: how the first officer plans the contributions, how it reviews and accepts one exact revision of each, how a separate editor receives only what was accepted, and how the assembled result is retrieved as the canonical document. It describes shipped behavior at source revision [`dff3741`](https://github.com/MachineWisdomAI/hermes-helmet/tree/dff3741479233d3e04157907ac163036e2affe9f). It is a retrospective account, not a proposal, and it does not claim the design was approved before or after it was built.

The identity rules it relies on are in the [identities and delegated authority Blueprint](https://github.com/MachineWisdomAI/hermes-helmet/blob/dff3741479233d3e04157907ac163036e2affe9f/docs/blueprints/identities-and-delegated-authority.md). The way files move between the first officer and a worker is in the [task artifacts Blueprint](https://github.com/MachineWisdomAI/hermes-helmet/blob/dff3741479233d3e04157907ac163036e2affe9f/docs/blueprints/task-artifacts.md). Neither contract is repeated here. The reference documentation is [Iterative writing with revision-bound review](https://github.com/MachineWisdomAI/hermes-helmet/blob/dff3741479233d3e04157907ac163036e2affe9f/docs/helmet-write.md); the first officer's instructions are in the [`helmet-write` skill](https://github.com/MachineWisdomAI/hermes-helmet/blob/dff3741479233d3e04157907ac163036e2affe9f/skills/helmet-write/SKILL.md).

The workflow is for writing that splits into parts, such as a report with sections. The documentation says a short edit or a review-only request should bypass it and go to one worker or be done directly. It is separate from the GitHub issue flow: it adds no queue, scheduler, database or content validator, and keeps its state in native Kanban tasks, runs, comments and attachments.

Throughout, the example is a hypothetical two-contribution document with a "shipped" section and a "next" section.

## Roles, kept apart

Three kinds of actor take part. The first officer is the coordinator. It plans, reviews, accepts, requests changes, releases the editor and replaces a contribution when needed, and it runs as its own Hermes profile. A section writer produces one contribution and submits it with the native request-review call. The editor is a separate card that assembles the final document from accepted inputs only. You, the Captain, delegate to the first officer; you do not relay comments between writers.

Most of the separation is written instruction, not code. The documentation and the skill say a writer never accepts, unblocks a card, creates cards, or touches another writer's file or the final document, and that the coordinator writes neither sections nor the final document. The skill also tells the first officer never to complete a section card itself or unblock the editor by hand. Those are rules for the agents that read them. The code enforces a narrower set: the coordinator profile must differ from every writer and from the editor (`plan` refuses a plan where it does not), the reviewing identity must be the planned coordinator, and the editor is released only by a command that checks acceptance.

Writers and the editor may share one writing profile, such as the `writing` profile in the setup recipe, because each works its own card in its own session. The recipe configures a native `default` profile as coordinator that never runs a model worker, and dispatches only the `writing` profile.

Worker cards receive writing guidance only: audience, purpose, format, voice, sources, the submit-and-revise loop, and the editor's fidelity and cut rules. A test in the pinned suite, `test_document_workers_get_writing_guidance_not_captain_authority`, is written to check that these cards contain none of a list of Captain, merge and policy terms.

## Readiness before the first card

The skill starts with a readiness check for every profile that will execute a card, including any replacement writer you might later switch to. Each writer, editor and replacement executor must be dispatchable, which means it appears in the worker's `kanban.dispatch_profiles`. The coordinator is the exception: it is the native `default` profile, never runs a model worker and is deliberately not in that list. Each executing profile must also be fresh, which means `helmet write profile-check` reports no findings and its guidance skill is discoverable. The board must exist too. A fresh worker has only the `default` board, and `plan` fails with `kanban_command_failed` rather than creating one.

Fresh context is a configuration check, and the documentation is specific about what it covers. A writing card should start from its sources, guidance, the previous artifact and the feedback. Hermes natively adds a list of the assignee's recent work on other tasks. The `helmet-writing-context` plugin removes that section from what `kanban_show` returns, for cards created by `plan` only. Memory files, the user profile, an external memory provider and `session_search` are profile settings, not per-task ones, so the recipe turns them off for the writing profile. `profile-check` reports any that remain on, and a profile that has not enabled the plugin.

The limits are written down. Hermes hooks fail open, so a missing or disabled plugin removes nothing. A retrieval tool an adopter adds some other way, such as an MCP server, is outside the check. The plugin acts where the worker reads context, not on the dispatcher's spawn prompt. The pinned documentation describes a regression test that runs the real context builder in an isolated home with an unrelated task marker and a memory marker. That test shows the marker present natively and excluded after the plugin transform, while sources, feedback and revision history stay.

## From plan to cards

The first officer writes one plan file naming the project, format, audience, purpose, guidance, the coordinator, the editor profile, and for each section a key, brief, sources and optional input files. For "shipped" and "next", each contributor gets only its assigned sources and the neighboring passages it needs, not the whole source collection.

`plan` is arranged so that nothing is runnable while the plan is incomplete. It reads every input file first, and a missing or oversized file fails before any card exists. It then creates the section cards held in the `blocked` state, attaches and verifies their inputs, and creates the editor card held and linked to exactly those sections. Only then does it release the held sections. A transport failure leaves held cards that no dispatcher claims, and rerunning the same plan finishes the job.

Each card records a fingerprint of the validated plan and the SHA-256 of each input file. The same plan reuses its cards. Any different plan for the same project key fails with `plan_changed` before it creates anything, because the cards cannot be amended in place. The documented ways to change course are to replace one part with `supersede` or to plan under a new project key. Adding a section to a live project is stated to be unsupported, since native Kanban has no supported way to add a parent to a card that may already be claimed.

## What a revision is

A submission is identified by a revision token, `helmet-write-revision:v1:BOARD:TASK:RUN:ATTACHMENT_ID:SHA256`. It names the card, the native review-request run, the staged attachment and its checksum. The attachment is the one the writer's request-review created, and its reference follows the contract in the task artifacts Blueprint. The first officer retrieves the file with `helmet artifact download` and reads it against the card's sources.

Every upload is a new attachment, so earlier revisions stay readable through `helmet write history`. A later file with the same name cannot replace an accepted revision, because acceptance names the attachment id and checksum. The command output is JSON that describes the artifact and never prints file contents. The first officer does not decide what is current by memory; every review and acceptance names an exact revision.

## One accepted contribution and one request for changes

Suppose the writer of "shipped" submits a first draft and the writer of "next" submits independently. The card for "shipped" moves to review with the first officer as assignee. `helmet write submission` prints the token for that run. After reading the draft, the first officer finds paragraph two too loose and runs `request-changes` with that token and concrete feedback.

Before anything changes, the command re-reads the card. It refuses with `stale_revision`, `not_in_review` or `revision_task_mismatch` if the card is not awaiting review, has a newer submission, or the token names another card. It also refuses with `self_review_refused` or `review_owner_mismatch` if the reviewer is the writer or the submission was routed to someone other than the planned coordinator.

Identity is checked through the Hermes runtime that executes the command, not the local `HERMES_PROFILE` variable. The card must appear in that runtime's own list of cards in review that it holds. Any other profile, including a distinct writer, fails with `reviewer_identity_mismatch` and changes nothing. `accept` makes the same checks.

When those checks pass, `request-changes` uses the native `reopen-review`. The card returns to ready, the assignee is restored from the review request, and the feedback is recorded as a comment naming the reviewed token. This is real dispatch; a comment alone dispatches nothing. A new session of the same writing profile starts from the card's body, the previous attachment and the feedback, which the pinned test checks by reading the task context for all three.

The writer revises, uploads a new file and requests review again. The new submission has a different token. If the first officer tries to accept the first token now, `accept` refuses with `stale_revision`, and the first draft is still downloadable. The first officer reads the second revision, then runs `accept` with its token and records each editorial decision the editor must honor, for example "Keep the March figure." Acceptance completes the card from review with run metadata that names the revision, the artifact reference and those decisions. `accept` then re-derives the accepted revision from the native runs and fails with `acceptance_unverified` if it is not the one reviewed.

The decisions are the only channel from review to editor. The skill says a raw review comment is never promoted to a requirement, so only `--decision` text recorded at acceptance reaches the editor. The skill also says to revise for clarity and fidelity before compressing length. The "next" section is accepted on its first submission in the same way, and its acceptance does not depend on what happened to the other card.

### Two rounds that did not work

Each `request-changes` records feedback and returns the same card to the same writing profile. `history` and the `request-changes` result report `escalation_due` once two rounds have been requested (the constant is 2 in `writing_review.py`). The [review reference](https://github.com/MachineWisdomAI/hermes-helmet/blob/dff3741479233d3e04157907ac163036e2affe9f/skills/helmet-write/references/review.md) says to stop after two rounds that did not fix the same issue and change the approach: clarify the sources and restate the brief, or supersede with another writer. The code counts changes requested. It does not judge whether the same issue recurred, and it does not itself change anything. The decision to change approach is the first officer's, so this is written guidance backed by a counter, not an enforced stop. Earlier failed submissions stay readable in the card's history and are not deleted.

### A submission with no attachment

A submission counts only when the review run names a file that matches one native attachment on the card. If the run lists none, or the name matches no original attachment, `submission` fails with `submission_artifact_missing`, and two matches fail as `submission_artifact_ambiguous`. The hint says the file must be inside the card workspace when review is requested. The coordinator can neither review nor request changes against a revision that has no token. The sources describe the cause but no dedicated repair command, so none is described here. The task artifacts Blueprint adds a documented rule that a handoff declaring an artifact the runtime cannot find must stay retryable rather than complete. That Blueprint's own reading found no code enforcing it, so treat it as intent.

## The race the code cannot close

Native `reopen-review` and `complete` take no revision argument. A competing session could change a card between the command's re-read and the native call. The documentation says this gap cannot be closed above the native API and advises one coordinator per project. The code narrows it. Both commands re-read after the slow artifact check and immediately before the native call, then verify the outcome afterwards.

If a newer submission lands during `request-changes`, the native call has already sent that newer card back with the old feedback. The command then adds a comment saying the feedback belongs to the older revision, fails with `request_changes_conflict`, and never reports success for the older token. If the dispatcher claims the card before the command reads it back, a running card counts as delivered only when the native record ties it to this feedback. The record must show the same writing profile, a later claim, and exactly one `CHANGES REQUESTED` comment naming the token. Anything else fails with `request_changes_unverified`. `accept` reports a different outcome afterwards as `acceptance_superseded` or `acceptance_unverified`. The pinned tests cover these paths against scripted fixtures.

## Releasing the editor

The editor card is created `blocked`, and a blocked card stays blocked even when all its parents are done. Native Kanban lets a running writer complete its own card, which would normally promote dependents, so `helmet write release-editor` does not trust dependency state. For each section it requires an accepted run that carries a record for the card's latest submitted revision, made by the planned coordinator and not the submitting writer, and it requires the accepted file to be retrievable by attachment id and checksum. Failures are `acceptance_unbound`, `self_approval`, `acceptance_superseded` and `accepted_artifact_missing`, and the editor stays blocked.

In the example, releasing after only "shipped" is accepted is refused. The pinned end-to-end test checks exactly that, and shows the editor ready after both sections are accepted. The release copies each accepted file to the editor card as `CONTRIBUTION-rRUN-NAME`, writes the revisions and the first officer's editorial decisions into a "Current accepted inputs" block in the card, and unblocks it. Only the accepted file for each section is copied; the first "shipped" draft, which was sent back for changes, is not. The editor works from that block.

The skill forbids completing a section or unblocking the editor by hand. The release command is the path that unblocks the editor after its checks; the skill's prohibition, not the command, is what stops a hand-made shortcut.

## Replacing an accepted contribution

Native Kanban has no command to reopen a finished card, so `helmet write supersede` replaces instead. It creates a new card from the old one with the same sources, a note carrying the reason and the prior accepted revision, and the same writer profile unless you name another. It links the new card to the editor in the old one's place, comments on the old card, clears the editor's recorded accepted inputs and holds the editor again, returning it from review if it was awaiting acceptance. The prior card, its attachments and its run history stay as they were. The replacement is then accepted and the editor released again with the new revision. In the unit tests, the old editor submission can no longer be accepted after this happens.

Supersession has limits, and the documentation states them plainly. It refuses when the editor is running (`editor_running`) or already done (`editor_done`), so it never cancels a running editor. It does not block or cancel the old section card, so an old contribution that is still running, or gets retried, can continue beside its replacement. Reclaiming a card is a same-card retry, not a hold, and reclaiming an editor does not stop it being dispatched again before `supersede` runs. When the controls the first officer is authorized to use cannot hold or retire the old execution, the review guidance says to report that blocker and the decision needed, and not to claim the replacement is isolated. No safe cancellation and no automatic replacement appear in the code, and recovery of a stalled editor or unfinished output is described as deferred.

An editor that read an input before the supersession may already have used it. What the code guarantees is that the current input record no longer lists the superseded card, and that a later acceptance of the editor's work is refused with `editor_inputs_stale` while the recorded inputs differ from each section's accepted revision. The documentation states that the editor never sees an input whose card was superseded; read that as describing the current record, not as a promise about what the editor already read.

## The editor and the canonical document

The editor assembles the document from the accepted files and decisions. Its card says to read the complete assembled artifact for continuity and fidelity before submitting; that is an instruction to the editor, not a check the code performs. It submits with request-review, and the first officer reviews that file as an exact revision, the same way it reviewed the sections. The skill asks for two separate reports: structural checks such as whether the file opens, required text is present and table values are right, and a source-based editorial assessment. Acceptance is refused with `editor_inputs_stale` if any recorded input is no longer its section's accepted revision.

After acceptance, `helmet write canonical BOARD EDITOR --output PATH` returns the editor card's accepted revision as the canonical document. It first re-derives that acceptance from native runs, checks that the editor's inputs are still current, and refuses a section card with `wrong_card_role`. Only then does it download the accepted attachment. The bytes it writes are the bytes that were accepted, and a later file with the same name cannot replace them because acceptance names the attachment id and checksum.

That is a statement about integrity. As the task artifacts Blueprint puts it, a successful download says the reviewer now holds the revision the reference named; it does not say the work is good. Acceptance is the first officer's judgment under delegated authority, and in this workflow that judgment does not wait for a person. A human is not a required step between a clean exact-revision review and release, though the Captain can always inspect the history.

The fresh-context settings are checked by configuration, with the gaps listed above. Fixtures and scripted workers show the code paths behave as the tests assert; they do not show that a particular deployment is configured as described. The "shipped" and "next" document is hypothetical. This account does not claim retrospective design approval.
