# Hermes Helmet worker runtime and model choice

*A retrospective Blueprint by Machine Wisdom AI.*

If you already delegate work to coding agents, two questions decide how much of your architecture survives the delegation: where the worker runs, and which model does its thinking. Hermes Helmet answers both with a split that follows authority. This document describes that split as it exists in the public source: where each actor runs, what state persists where, how the worker's provider and model are chosen and checked, and where the design is known to break.

It is a retrospective account of existing behavior. It does not claim the design was approved after the fact, and it does not describe a live run. The evidence scope at the end says what was read and what was not exercised.

## Three actors, three kinds of choice

Hermes Helmet separates three things that are easy to run together: which coding agent acts as your first officer and which model it uses, which provider and model Hermes uses to do the work, and whose authority each actor holds. Changing one does not change the others.

The Captain holds the goal and the delegation. The first officer is the coding agent on your own machine. It acts under the Captain's OS account and GitHub identity. The worker is Hermes, running in a Docker container under its own GitHub account and credentials. If you move the worker from one provider to another, Hermes keeps that account, the repository policy still decides what it may touch, and merge authority stays with the first officer.

The first officer's host and model are your decision, made in that agent's own tooling. The provider and worker-role files in the pinned source do not configure it, so nothing below selects, validates or switches the first officer's model. The one place the model documentation touches the first officer is consent. A policy flag, `captain_model_provider_consent`, records standing consent for accepted task and review content to be sent to the configured worker provider. When it is `true`, Captain skills do not ask again per task, model or provider. When it is omitted or `false`, they honor earlier task-specific consent or obtain it first. The documentation says this is an instruction-level record, not a runtime egress guard, and that changing credentials, billing, scope or provider configuration is always a separate decision.

## Installation, image and deployment are different things

The same split shows up in how the pieces arrive. The `helmet` CLI and the bundled first-officer skills come from a source checkout on the host. The worker comes from a published container image that Docker Compose pulls and starts. The quickstart says directly that installing the CLI does not pull the image or start Docker, and that the CLI does not start or restart the worker. ([quickstart](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/docs/quickstart.md), [runtime image](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/docs/runtime-image.md))

There are three artifacts, and the documentation keeps them apart.

The host CLI is installed by cloning the public repository, creating a virtual environment and running `python -m pip install .`. Current source installs `helmet` and a compatible alias, `hermes-helmet`; the Python package is `hermes-helmet`.

The published worker image is, at this source pin, described as a preview. The runtime-image document at the pin records a preview image identified by digest and a package label of `0.2.0`, which that document says is not a stable release and not the dated Python wheel. That is historical preview guidance. It is not authority for what is current, so this document does not call that image the current stable runtime or repeat its digest and version instructions. For installation, follow the maintained [runtime-image guidance](https://github.com/MachineWisdomAI/hermes-helmet/blob/main/docs/runtime-image.md). Two properties of the design hold regardless of which image you use. The documentation pins images by digest rather than by a mutable tag, and the build commit is recorded in the image so you can check it. Inside a running container, `/opt/hermes-helmet/SOURCE_COMMIT` holds that commit. At the pin, the documented build commit is earlier than the revision the documentation is pinned to, so a document and the image it points to need not be the same snapshot.

Your running deployment is the third thing: a particular container, its named volume and its policy file. Replacing the image does not replace the volume, and a source checkout on the host says nothing about what the container is running. The commit file is how you tell them apart.

## What lives where

The public Compose file defines one service, `hermes`, running `gateway run` as non-root UID and GID 10000 with `restart: unless-stopped`. It publishes the dashboard port on the loopback address only and mounts three things.

A named volume, `hermes_helmet_state`, is mounted at `/opt/data`. This is the worker's persisted state. The runtime-image document lists what lives there: worker configuration, credentials, repository checkouts, the poller ledger, and the associations between issues, tasks and pull requests. Provider credentials are entered through the profile's own login inside the container and stay in owner-only files on this volume.

The authority policy is mounted read-only from the host at `/opt/hermes-helmet/config/policy.mounted.json`. It is a secret-free JSON document naming the Captain and worker GitHub logins, the assignee profile, the dispatch label and the repository allowlist, including each repository's worktree path inside the container. At startup the entrypoint copies it to `/opt/data/github-issue-poller/policy.json` on the volume, and intake and the poller read that copy, not the mount. The quickstart notes that the mounted file must be readable by UID 10000, and that you restart Compose after editing it so the copy is refreshed.

A tmpfs at `/run/hermes-helmet` holds the worker's GitHub token. Compose injects the token as `GH_TOKEN` and `GITHUB_TOKEN` only so the entrypoint can write it to an owner-only file on the tmpfs. The entrypoint then removes the raw variables before it starts the upstream init chain, so supervised processes do not inherit the token. A wrapper at `/usr/local/bin/gh` reads the file for each authorized GitHub command. The Compose comments and the quickstart say this. The entrypoint script is not among the pinned sources, so variable removal is documented intent, not observed code.

The host keeps its own state. The optional `helmet setup` wizard writes a policy and owner-only secrets under `~/.hermes-helmet` and installs the bundled skills. The quickstart is explicit that it does not start Docker, does not write the Compose environment file and does not mount its output into the container. The host policy and the container policy are separate files unless the worktree paths happen to be valid in both places. Often they are not, because the worker's checkouts exist only inside its volume.

## One operation, end to end

A representative path starts with the Captain's plan recorded as a GitHub issue.

On the worker side, you prepare the environment file and policy, point `HERMES_HELMET_IMAGE` at the image digest you chose, and run `docker compose pull` followed by `up -d --no-build`. You then clone each allowlisted repository into `/opt/data/repos` inside the container with the worker identity, using a credential helper that calls the `gh` wrapper. Next you create the assignee profile, set its provider and model, and log in to the provider in the container. The quickstart asks for one single-turn smoke call before installing the poller cron job. These `hermes` commands are the in-container Hermes Agent CLI, not the host `helmet` command, and the quickstart repeats the distinction.

On the host, the first officer reaches the worker through the CLI. The quickstart's commands cover issue and epic runs, `status` and a read-only `wait`. A label on an allowlisted open issue (by default `hermes-kanban-go`) makes the poller create exactly one linked Kanban root task, and repeating intake reuses it. The worker implements and opens a pull request. When trusted review activity appears on that pull request, the poller creates one dependent repair task on the same PR. The worker does not merge and does not force-push. The documentation states that task completion alone does not accept or merge the pull request; the first officer reviews heads and applies the merge gates under its own authority.

The reference adapter in `compose_runtime.py` shows the host-to-container seam in code. A first officer can set `HERMES_HELMET_HERMES` or `HERMES_HELMET_WORKER_RUNTIME` to `helmet-compose`. Each call then becomes `docker compose -p PROJECT exec -T hermes ...`, and the process is replaced by Docker through `exec`. Standard input and output pass through unchanged and the exit status is the container command's. `COMPOSE_FILE` and `COMPOSE_PROJECT_NAME` must both be set; nothing falls back to a default project. The adapter supports `kanban` and three artifact verbs. It refuses the coding workflow's ledger, dispatch and wait verbs, and any other verb, with exit status 2, since those belong to a deployment's own adapter. It pins the in-container actor to `default` regardless of host profile variables. Its source docstring frames it around a separate writing project, so it is one seam, not the route the coding quickstart takes.

## Where the worker's model is chosen

The worker's model is a setting on the worker, not on the first officer. In the quickstart's profile step, you set `model.provider` and `model.default` on the assignee profile inside the container and add the provider credential with `auth add`, which prompts locally so no secret appears in a command or file. Those values are meant to match the policy's `inference_provider` and `inference_model`, and the private-overlay document says the same. The quickstart's example uses one provider and model; a Claude subscription route has its own guide, which is outside the pinned sources. The quickstart's cron install uses `--skip-model-config` so that the profile you configured and smoke-tested is kept rather than rewritten.

In the policy, the provider and model sit apart from authority. The policy names models, base URLs, timeouts and embedding dimensions, never credentials; provider keys and tokens stay in owner-only runtime files or the process environment. The same policy file also holds the committed identities, repositories, merge permissions and capacity, so choosing a model is a different kind of statement from granting authority. The worker's GitHub identity comes from its own token and the merge rules sit with the first officer. The documentation's structure therefore implies that changing the worker's provider or model leaves both alone. No pinned source tests that implication, so treat it as design intent.

Model lanes are a second layer. The Hermes executor is one lane. Optional FAVA Trails generation, OpenViking semantic generation and embeddings are three more, each with its own chat-completions or embeddings contract. A `model_lanes.hermes_executor` override is accepted only when its provider and model match `inference_provider` and `inference_model`, so the lane document cannot quietly contradict the policy. The source also refuses to treat one model artifact as suitable for several lanes unless there is independent probe evidence, and it requires generation and embedding models to be probed as separate contracts. If you decline every optional lane, the minimum runtime still works. The public Compose stack does not start a local inference server. The policy's integration flags for OpenViking, FAVA Trails and Signal are false in the quickstart's example, and the documentation says to leave them off until their own guides apply.

Worker roles are independent of lanes. The documentation says model lanes select inference providers and worker roles select assignments. Roles map to profiles (builder, reviewer, writing), with a global in-progress cap and a per-profile cap. Issues default to the builder, a `Worker role: writing` declaration routes to the writing profile, and a native GitHub review request routes to the reviewer. Each role can carry its own reasoning effort (`low` through `max`). Provisioning writes that effort against the policy's model and, for managed selections, against the backup models too, so a role keeps its effort when the model changes.

## Checking the choice

Two checks answer two different questions.

The first is whether the configured endpoint answers correctly. `helmet models setup --probe` and `helmet doctor --live` do this. Without `--probe`, setup reports the minimum runtime as operational but not validated (`setup_success=false`). A chat probe posts a tiny prompt to `{base_url}/chat/completions` and needs a usable assistant message; an HTTP 200 whose body is `{}` or an error object fails, and a lane with `structured_output` enabled must return JSON. An embeddings probe needs a finite vector whose length equals the configured dimensions, followed by a retrieval check over a throwaway in-memory index that never touches production data. The always-selected Hermes executor must pass its probe before setup reports success.

The code also refuses several things outright: base URLs that embed credentials or carry a query or fragment; a `loopback` bind whose host is not `127.0.0.1`, `localhost` or `::1`; a `container-host` bind that is not `host.docker.internal` or loopback; and runtime credential files that are symlinks, are not regular files, or are readable by group or others. Live probes refuse a cross-origin redirect while a credential is attached, and they fail closed on timeout. Changing an embedding model, dimension or quantization is refused until you pass `--reindex-confirmed`, and the new fingerprint is saved only after every required probe succeeds. Restoring the previous fingerprint needs `--index-restore-confirmed`, because swapping metadata alone does not restore the index.

The second question is whether the worker profiles actually match policy. `worker_role_runtime --verify` compares each profile's provider, model, turn budget, reasoning effort, capacity limits and delivered company contract against the accepted policy, and reports drift by profile name. It also asks GitHub, from each profile's own home with token variables removed, which account the profile resolves to, and fails on a mismatch with the configured worker login. That is how the source ties model configuration back to identity: a profile on the right model but the wrong account does not verify.

## Switching routes and recovering

For day-to-day changes there is `helmet providers`. You configure an ordered list of routes, for example a primary and a backup, with `helmet providers configure --route primary=PROVIDER:MODEL --route backup=PROVIDER:MODEL`. Configuring selects automatic mode, where the first route is primary and the rest become native Hermes fallbacks in order. `helmet providers use backup` pins exactly one route with no fallback, and `helmet providers auto` restores the ordered chain. Model IDs are explicit, so a named route does not silently move to a newer release. The selection file is secret-free and carries a version, up to sixteen routes and the selected name.

Recovery from a provider failure belongs to Hermes Agent, not to Hermes Helmet. The documentation says Hermes owns failover and return to the primary, that supported triggers and timing depend on the installed Hermes version and provider adapter, and that there is no Hermes Helmet retry loop or quota polling service. It also says to validate a subscription adapter's actual quota error and recovery before claiming live acceptance. The pinned sources show no exercised live failover. Treat automatic fallback as documented intent that the projection code supports, not as observed behavior.

What Hermes Helmet does enforce is how the selection reaches the worker. The projection changes model settings and preserves identity fields. It refuses to replace an endpoint-bound executor lane and refuses a profile that carries its own endpoint or credential overrides, so a switch never carries an old endpoint or key to a new provider and never discards credentials. A managed selection removes the legacy `fallback_model` entry, since Hermes would otherwise append stale routes. Applying a change goes through a deployment-supplied transport, set with `HERMES_HELMET_WORKER_RUNTIME`. The documented contract requires that deployment to authenticate the operator, serialize its selection record and require drained workers. When the transport rejects an operation, the error tells you to run `providers status` and check Captain identity, paused dispatch and drained tasks. Because the transport is the deployment's, how well any of this works for you depends on that adapter. Nothing in the sources promises that it ports unchanged to another environment.

Identity has its own recovery path. Provisioning links an unchanged stock builder persona to the accepted company contract and first copies the original to a private backup directory outside profile, skill and memory discovery. While workers are drained, `worker_role_runtime --recover-identity PROFILE` stages and validates the replacement before swapping it in, so a blocked temporary path or failed write leaves the prior identity untouched. A custom persona or an unexpected symlink is left byte-identical, and verification then reports action required instead of success. Failed provisioning restores modified files and removes newly created profiles and links. Provisioning also copies provider settings, `.env` and Git config from the approved builder profile but leaves each profile's histories, OAuth stores, memory and cron separate. That is the isolation the source implements: isolation between profiles under one worker state root, applied while the worker is drained. The source does not claim it protects against a compromised host, and it does not promise that the same layout carries over to other runtimes.

## Company overlays

The public configuration seams are few. `HERMES_HELMET_IMAGE` selects the image. `HERMES_HELMET_POLICY_HOST_PATH` selects the policy file. `HERMES_UID` and `HERMES_GID` set the container user, `HERMES_DASHBOARD` and the dashboard host port control the dashboard, and the optional Claude subscription token has its own variable.

A company that wants its own policy and deployment settings keeps them in a private repository that depends on the published image by digest. The overlay document is firm about what not to do: no fork of the core, no submodule, and no replacement control loop mounted over `/opt/hermes-helmet`. The image owns the runtime, the entrypoint, the `gh` wrapper, the UID and the state layout. The company owns the policy, the allowlist, both GitHub identities, the token and provider credentials, and a uniquely named volume. Sharing the public volume name across deployments would mix state. When a company needs extra files, a thin image may inherit the digest, keep the entrypoint and the UID, and add files. The overlay's examples use a fictional ExampleCo and do not describe a real deployment.

## Where this breaks

The documented failure modes are mostly about mismatched views of the same state.

- A shell variable left from an earlier session overrides the image setting in the environment file, so the wrong image can start.
- A policy file the container user cannot read is invisible, and startup cannot copy it.
- Host diagnostics cannot see checkouts that exist only in the worker volume.
- Changing a repository slug or worktree under a running intake can attach new work to the wrong tree. Pause the poller job, let active tasks finish or reconcile them, and only then change the pin.
- Removing the dispatch label from open issues stops new issue dispatch but does not pause the review-repair poller, which is why the pause goes through the cron job.
- Recording a blocker does not cancel a task.
- Rolling back means setting the previous digest against the same volume.

Provider changes add their own failures: a transport that rejects an operation because workers are not drained, a profile that verifies on model but fails on account, and an embedding change refused until the index is rebuilt. In each case the source refuses rather than proceeds.
