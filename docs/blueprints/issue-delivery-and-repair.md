# Hermes Helmet issue delivery and repair

A retrospective Blueprint for [Hermes Helmet](https://github.com/MachineWisdomAI/hermes-helmet) from Machine Wisdom AI, describing the issue-to-acceptance loop as it shipped at source revision [`5360dcd`](https://github.com/MachineWisdomAI/hermes-helmet/tree/5360dcd1637d92c7934cca4ce0c015c5c5befbd2). It is a description of existing behavior, not a design proposal. The [identities and delegated authority Blueprint](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/docs/blueprints/identities-and-delegated-authority.md) holds the full identity contract. This document repeats only the parts the issue flow depends on.

The Captain is you. The first officer is your coding agent, acting with your delegated authority under the Captain's GitHub login. Hermes is the crew, working under its own worker login. The document follows one issue from delegation, through a pull request, a review that requires repair, merge and acceptance, and then explains how the same machinery resumes interrupted work. An evidence scope at the end says what the description rests on.

## The loop and who owns each step

The skill gives the first officer a loop: preflight, dispatch, wait for a pull request, review the head, request a repair, wait for the repair, mark the work ready, pass the merge gate, merge, verify the merge, done ([`docs/helmet-issue.md`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/docs/helmet-issue.md)). Two design choices keep that loop from turning into a second project-management system.

First, the first officer never creates repair work. Its only output from a review is a formal GitHub review. The issue poller, `github-issue-poller`, is documented as the sole creator of repair tasks, and the skill lists a second repair relay as a pitfall because it would duplicate the poller ([`SKILL.md`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/skills/helmet-issue/SKILL.md)). The documentation lists "no second watcher, webhook, repair relay, queue, or worker checkout" as a non-goal.

Second, the first officer keeps a small checkpoint, and GitHub stays the record of the review itself. The checkpoint is a non-secret JSON file on the Captain host, keyed by the issue URL. It holds the run's state, the root task id, the pull request URL, the reviewed and clean head commits, the repair round count, the merge mode, the original start time and structured blocker codes. It holds no tokens. [`record_review_result`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L1902) discards the review summary before saving, so review prose never reaches the checkpoint.

## From accepted issue to a discovered pull request

You and your coding agent agree on a written plan and record it as a GitHub issue. Creating the issue authorizes nothing. Delegation starts when you ask the first officer to carry the issue through with `helmet issue ISSUE_URL --config /path/to/policy.json`. The documented outcome of that first pass is a checkpoint past preflight, a recorded root task or a precise blocker, and, later, a discovered worker pull request. The states covered in this part are `PREFLIGHT`, `DISPATCH` and `WAIT_PR`.

### Preflight and adoption in one pass

The function that does the work is [`run_preflight_and_adopt`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L2566). The first officer runs it as the Captain. Its inputs are the issue URL, the authority policy, the poller ledger path and the checkpoint directory. It loads the checkpoint for the issue, or starts a new one in `PREFLIGHT` with the policy's default merge mode.

It checks authority before it reads anything about the work. GitHub must report the Captain's login. The worker's login must not appear among the credential profiles `gh` stores on the Captain host. The policy must be version 2, name both logins, keep them different, and carry valid budgets. A failure in any of these stops the pass with a coded blocker such as `captain_identity_mismatch` or `worker_profile_on_captain_host`, and the pass saves that blocker into the checkpoint as fatal.

Next it loads the issue through [`load_issue`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L848). The repository must be in the policy allowlist, or covered by a named-request enrollment. A pull request URL is refused. This is also where routing is resolved: the issue's labels are matched against the operator's `issue_routes`, and labels that select different targets raise `route_ambiguous` instead of being guessed. A routed issue stays the tracking and acceptance identity, while the checkout, branch and pull request belong to the implementation repository, as [`docs/issue-routing.md`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/docs/issue-routing.md) documents. The routed branch is an opaque `automation/tracked-<hash>` name, so the branch name does not identify the tracking issue. An unrouted issue uses `automation/<repository>-<number>`.

The pass then settles the merge mode and the budgets. An explicit choice passed in, or inherited from an epic, is recorded and ends the question. If the policy, issue or epic text already requires explicit Captain approval for merging, that authority is recorded without asking. With no choice by either route, the pass asks only when the run is a session continuation (`host_continuation` is `session`) and the issue is not covered by a named-request enrollment. It then saves `merge_choice_required` and stops, so the first officer asks you once before anything is dispatched. A named-request enrollment counts as explicit delegation for that repository, so the pass records the policy default as the merge mode, notes `named_request_unattended_default` and continues. Any other run, including a scheduled one, also uses the policy default without asking. A saved manual choice is never overwritten by the default. Explicit merge authority can still require separate approval at the merge gate, described below.

An exhausted time budget ends the pass with a fatal blocker before any mutation. A closed issue is refused unless a merged pull request already exists, in which case the checkpoint goes to `DONE`. An open issue must carry the policy's ready label or its dispatch label. If it carries neither, the pass raises `issue_missing_ready_or_dispatch_label` and refuses a silent dispatch.

A separate [`preflight`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L1500) function validates the same conditions and returns the issue, the observed login and the merge mode. A search of the pinned `src` tree finds `run_preflight_and_adopt` called from the CLI and the epic orchestrator, and finds no source caller of `preflight`; only tests call it. The delivery path therefore runs the inline copy of the checks inside `run_preflight_and_adopt`.

### Discovery comes before any change

Before the pass changes a label or creates a task, it calls [`discover_progress`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L1645), which only reads. It looks for an existing root task in the poller's SQLite ledger, and when the local ledger has none, asks the configured worker runtime. It reads the ledger's pull request watch. When there is a root task, it reads that task from Kanban and takes the pull request URL from the task's run metadata. It also asks GitHub for candidate pull requests, in one of two ways. A read failure from Kanban raises an error and is never taken as absence.

The result is a root task id, a canonical pull request or none, and a repair task id. Choosing the canonical pull request is strict. A pull request belongs to the issue only through the canonical branch, a closing keyword aimed at this issue (unrouted issues only), or exact adoption of its URL from the ledger or Kanban. Its author must be the configured worker, and two open worker pull requests that the canonical branch cannot tell apart end the pass instead of being resolved by a guess.

The two lookups differ. For an unrouted issue, [`discover_linked_pull_requests`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L1201) reads the issue's timeline cross-references. For a routed issue it never consults the tracking issue's timeline. It lists pull requests, open or merged, in the configured implementation repository whose head is the opaque canonical branch, and loads each by number. The route and the branch are the only association.

The opaque branch keeps the tracking identity out of the branch name. It does not make the pull request content safe. [`docs/issue-routing.md`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/docs/issue-routing.md) states a privacy instruction: the worker keeps the tracking issue's URL, number, repository, title, body, labels, approval or merge-marker provenance and any closing keyword out of the pull request title and body, commits, branch name, replies and comments, and repair tasks repeat it. The documentation calls this an instruction plus structural safeguards, not a content scanner, and says to review the public pull request for leaks like any other change. Hermes Helmet's association never needs a link back, but the pinned code does not inspect content for such references.

### Dispatch: adopt the existing root or create one

With discovery done, the pass moves the checkpoint to `DISPATCH` and takes one of three paths.

If a root task exists, the pass records `adopted_root` and creates nothing. This is the usual result when you run `helmet issue` again after an interruption.

If no root exists but a canonical worker pull request does, the pass stops with `pr_without_recoverable_root`. The code comment gives the reason: creating a second root would duplicate work. The pass changes no label and creates no task.

If neither exists, the pass calls [`ensure_dispatch_label`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L1558), which adds the dispatch label through `gh` when it is missing, and then [`adopt_or_dispatch_root_task`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L1584). That function looks for an existing root a second time. If there is none and the local ledger file is absent but a worker runtime is configured, it asks the worker side to dispatch, so the Captain host never starts a second ledger. Otherwise it calls the poller's own `create_task_once`. The pass records `dispatched_root` or `adopted_root` according to the `created` flag it gets back, then runs discovery again so the pull request and ledger agree.

### One root task for repeated intake

The same function is the entry point for two actors. The first officer reaches it through the path above. The issue poller reaches it on its own schedule: [`run_once`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/github_issue_poller.py#L1460) first verifies the live GitHub login is the worker and fails before reading any issue if it is not. It then lists open issues carrying the dispatch label in each allowlisted repository, resolves each issue's route, and calls [`create_task_once`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/github_issue_poller.py#L1101). Since the first officer has just added the dispatch label, the poller will see the same issue on a later cycle. Both arrive at the same function with the same issue URL.

`create_task_once` is the idempotency point. It opens the ledger and takes a write lock with `BEGIN IMMEDIATE`. It maps a transferred issue's retired URL to its current one, then looks the URL up in the `issue_tasks` table. If a row exists, it releases the lock and returns the task id with `created` false. If not, it checks that the target worktree exists and is a Git work tree. It then runs one `hermes kanban create` with the title `<repository>#<number>: <title>`, the task body, the policy's assignee, the isolated worktree, the canonical branch, the completion contract, the runtime limit and `--idempotency-key` set to the issue URL. It inserts the new task id into the ledger and commits. Any exception rolls back the transaction, so a failed create leaves no ledger row.

This gives two layers: the ledger row, and the idempotency key passed to Kanban. The code shows the ledger layer in full. What Kanban does with the key is Kanban's behavior and is not shown in the pinned sources, so this document does not claim it. The repeated-intake guarantee that the code supports directly is the locked ledger lookup.

One difference between the two entry points is visible in the code. The worker-identity check lives in `run_once`. The first officer calls `create_task_once` directly, so that check does not run on that path.

### Worker implementation

Once a root task exists, the rest is the worker's. The task body is rendered from the issue and the policy, and a [fixture](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/tests/test_github_issue_poller.py#L1880) checks that it names the worker identity, forbids merging and force-pushing, and asks the worker to pass `metadata.published_pr` when it publishes. The completion contract is either the repository slug (the default) or `local-only`, and fixtures check that the task is created with whichever the policy selects. Both still ask for `metadata.published_pr`.

The documentation says the worker then takes the task, works in the assigned worktree, opens a tested pull request under its own account and closes its task. That sequence is documented intent. The pinned code and tests establish the instructions and the completion contract. They do not observe what a worker does after it starts, and polling alone does not invoke a model.

### Finding the published pull request

Two readers use the same metadata. The poller's [`_pull_request_url`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/github_issue_poller.py#L568) walks the root task's runs from newest to oldest and reads two keys from each run's metadata, `published_pr` and the older `pr_url`. A value counts only if it parses as a pull request URL. Two different valid URLs in one run raise "disagreeing pull request metadata". Malformed values are ignored. A `pr` key alone adopts nothing.

The poller then validates where the pull request lives. It must sit in the tracking repository, or in a configured route target of it. A routed pull request is accepted only when the task's workspace is a worktree inside that target's checkout. The poller keeps a watch row per issue and, while that row has no pull request, re-reads the root task on every cycle. Metadata that arrives late is therefore adopted without manual repair of the ledger. A pull request that is not open is not adopted. This watch is what the poller later uses to create same-PR repair tasks.

The first officer reads the same metadata through `discover_progress`, using [`_pr_url_from_kanban`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L1148), which turns a disagreement into `kanban_pr_metadata_disagree`. It combines that URL with the ledger watch and the candidates from the lookups above. A URL outside the implementation repository raises `pr_outside_repository`. A ledger URL and a Kanban URL that differ raise `ledger_kanban_pr_disagree`. The result goes through the canonical selection described earlier.

The observable result depends on what discovery finds. With no pull request, the checkpoint stays in `WAIT_PR`, with its root task id recorded, and `helmet status` reports no pull request. When a worker-authored pull request is found, the checkpoint records its URL and number and moves to `REVIEW_HEAD`, ready for the Captain's review of the exact head. Both outcomes are saved before the pass returns.

## A review that requires repair

Suppose Hermes has opened a pull request at head `A`, and the first officer's review in its own checkout finds a material defect: a supported failure, its consequence, and the requirement it breaks. The bundled review guidance asks for related symptoms to be grouped in one pass and for small wording points to stay nonblocking, so a review should not send the work back for cosmetic reasons ([`delivery.md`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/skills/helmet-issue/references/delivery.md)).

The first officer posts a formal `REQUEST_CHANGES` review as the Captain on `A`, then records the outcome with `helmet issue ISSUE_URL --record-review changes_requested --head-sha A`. That command reaches [`apply_review_outcome`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L3245), which does not take the first officer's word for it. In order, it:

1. Confirms the GitHub login is the Captain's and that the worker's credential is not stored on the Captain host.
2. Rediscovers the canonical pull request with `discover_progress` and fails with `review_head_mismatch` unless `A` is still the live head.
3. Fails with `checkpoint_pr_mismatch` if the checkpoint already names a different pull request.
4. Reads GitHub's reviews and fails with `formal_review_mismatch` unless the latest Captain review on exactly `A` is `CHANGES_REQUESTED`.

Only then does it update the checkpoint: the reviewed head becomes `A`, the clean head is cleared, a pending repair is flagged, the state becomes `WAIT_REPAIR`, and the repair round count goes up by one. A second `changes_requested` review on the same head counts as a new round, while re-recording the same review event does not, so a retried command does not spend the budget twice. The checkpoint, not the poller, is where rounds are counted. Once the count exceeds the policy's repair limit, `budget_exhausted` fails the run.

A test in the pinned suite checks this path with a fake runner: after recording `changes_requested`, the state is `WAIT_REPAIR`, a repair is pending, and the fake runner records no task creation ([`test_changes_requested_waits_for_h1_not_local_repair`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/tests/test_helmet_issue.py#L2285)).

## The poller creates the repair on the same pull request

The poller reads the pull request's GitHub timeline on each cycle for open pull requests it is already watching. [`_review_events`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/github_issue_poller.py#L688) keeps `reviewed` and `commented` events and drops anything from the worker's own login. Of the review events it keeps only those whose state is `changes_requested` or `commented`, so an approval creates nothing. The actor must be a trusted human, meaning a user whose repository association is on the policy list (owner, member and collaborator by default), or a bot whose exact login is listed in `trusted_review_bots`. Reviews from anyone else are ignored.

[`_reconcile_review_task`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/github_issue_poller.py#L869) then applies three rules:

- If the previous repair task for this pull request has not reached a terminal status, it creates nothing.
- Among events newer than the stored cursor, it takes only the latest one. Several reviews posted between two cycles become one repair task.
- It creates the task as a child of the previous repair task, or of the root task for the first repair, in the same worktree and on the same branch as the root task. The idempotency key combines the repository, pull request number, event kind and event id, so repeating a cycle cannot create a second task for the same event. It then saves the cursor and the new task id.

The task body treats the review as findings, not instructions. Hermes is told to fetch the current pull request, inline comments, checks and mergeability from GitHub, triage each finding against the source issue, fix valid ones on the existing branch, run the repository's required verification, and finish by pushing to the same pull request. The body forbids rebasing, force-pushing, opening a new pull request, merging, or expanding into unrelated cleanup ([`render_repair_task_body`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/authority.py#L1618)). Those prohibitions are instructions to the worker. The pinned code does not check what the worker does after it starts.

Two points are worth stating plainly. A pending or failing CI check does not create a repair. The pinned poller code queries pull request timeline review events and has no path from check results to a task, and the skill and non-goals say the same: no autonomous repair from CI failure alone. Also, the documentation describes the trigger as a trusted review, but the code also admits a trusted actor's plain `commented` event. That is observed behavior broader than the documented intent.

For a routed tracking issue, the same task is created in the implementation repository's checkout on the original branch, and the body adds a public pull request privacy contract so the worker keeps the tracking issue out of the public change.

## The new head is re-reviewed

When Hermes pushes the repair, the head becomes `B`. On the next pass, `run_preflight_and_adopt` compares the live head with the checkpoint's clean and reviewed heads. A new head clears any clean result, clears the pending-repair flag and sets the state to `REVIEW_HEAD`, even if the repair task is still shown as active. Otherwise, an active repair keeps the state at `WAIT_REPAIR`. A repair that finished without changing the head returns the work for first-officer reassessment when its task is tied to the current review event, because a finished task alone is not evidence of a fix. The documentation's section on legacy checkpoints covers older records that predate event-level tracking.

The first officer reviews `B` in its own checkout and posts a formal review. If it is clean, the first officer records it with `--record-review clean --head-sha B`. `apply_review_outcome` runs the same checks, this time requiring the latest Captain review on `B` to be `APPROVED`. On success the clean head becomes `B` and the state is `READY`. If the associated epic's original start window has already expired, the pass instead records a fatal budget blocker and does not mark the work ready. If the review is `changes_requested` again, the loop repeats with a new round.

An explicit `blocked` outcome is different. It needs no formal review, clears the clean head, and stops merging on that head until a newly accepted clean review or a new head recovers it. A test checks that an unchanged-head resume does not promote the state back to `READY` ([`test_blocked_review_invalidates_clean_and_blocks_merge_and_resume`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/tests/test_helmet_issue.py#L5353)).

## Merge

Merge is a separate command, `helmet merge ISSUE_URL --expected-head SHA`, run as the Captain. [`merge_issue`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L3980) does not merge on the strength of the earlier review. It rediscovers the canonical pull request and withholds the merge, recording a blocker in the checkpoint, when any of these holds: the head differs from `--expected-head`; the issue is not open; the repair budget or the original issue window is spent; a repair is still pending; a merge was already attempted at this head; or the review-only enrollment forbids merging.

It then reads the required checks for that SHA from branch rules or classic protection, including a configured GitHub App and both a same-name check run and commit status when both exist. Neutral counts as a pass. The result goes to [`evaluate_merge_gate`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L2020), which re-reads the pull request and requires all of the following:

- The head has not moved during the gate.
- The checkpoint's clean head equals the live head, and the latest Captain review on that commit is still `APPROVED`.
- The pull request is not a draft and is mergeable.
- Required checks are verified green.
- The associated epic window is still open.
- The merge authority allows it. By default the first officer may merge a clean head. A whole-line `Merge when clean: no` on the issue or its parent epic, or an installation set to explicit Captain approval, makes the gate stop for separate approval instead.

Under the `local-only` worker completion contract, GitHub's `clean` state is not treated as verified checks, and with no configured checks the gate falls back to explicit approval. A failing or pending required check therefore holds the merge; it does not trigger a repair.

If the gate allows it, `merge_issue` re-reads the pull request once more, withholds if it is draft, unknown or not clean, records the attempted head, and submits one squash merge request carrying `sha=<head>` so GitHub declines if the branch has moved. [`merge_pull_request`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L2165) then re-queries GitHub. A merge that cannot be confirmed leaves a blocked state with a code and is not retried. Running the command again after a confirmed merge reconciles and does not merge a second time. The worker never merges.

One caveat for readers who call the gate directly: when `evaluate_merge_gate` is given a live runner and no check evidence, and the policy is not `local-only`, it treats a live `clean` state as green checks. `merge_issue` always supplies the evidence it read, so the supported command does not take that route. A test in the pinned suite exercises the inference ([`test_github_pr_infers_required_checks_from_live_clean`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/tests/test_helmet_issue.py#L1424)).

## Merge, acceptance, release and publication are different events

For an issue implemented in its own repository, merging the pull request completes the work and the checkpoint moves to `DONE`. For a routed tracking issue, the code lives in the implementation repository and the tracking issue is the delivery and acceptance record. After the merge, the checkpoint moves to `AWAIT_ACCEPTANCE` and the tracking issue stays open.

Acceptance is its own command, `helmet accept ISSUE_URL --expected-head SHA`, handled by [`close_tracking_issue`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/src/hermes_helmet/helmet_issue.py#L4362). It repeats the Captain checks and refuses an issue that is not routed. It withholds acceptance unless the canonical pull request is merged at the named head and the checkpoint's clean head matches that head. A merge made outside the workflow, or at a head that never received a clean review, therefore leaves acceptance withheld with `head_lacks_clean_captain_review`. When the checks pass, it posts a comment naming the pull request and short SHA, closes the tracking issue as completed, re-reads it, and records `DONE`. If the re-read shows the issue still open, it records a close failure or `tracking_close_unconfirmed` and does not retry blindly. Work that waits on the tracking issue unblocks only when it closes. Closing the issue by hand is also recognized by a later pass if a merged pull request exists.

Release and publication are further steps that this loop does not perform. The pinned files contain no release or publish command, and the bundled review guidance describes code readiness, runtime acceptance and publication authority as separate claims. Acceptance here means the Captain recorded that the merged head is accepted for the tracking issue. It does not mean the change has shipped.

## Recovering interrupted work

Every `helmet issue` pass starts the same way whether it is the first or the tenth. It loads the checkpoint if one exists, checks the Captain identity, then runs the read-only discovery described earlier before any mutation, including the separate routed and unrouted pull request lookups. That discovery is what lets a new pass pick up where an interrupted one stopped.

Three rules keep resumption from duplicating work:

- **Adopt before creating.** If a root task exists for the issue, `adopt_or_dispatch_root_task` returns it and creates nothing. A test confirms that adopting an existing root creates no task ([`test_adopt_existing_root_never_duplicates`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/tests/test_helmet_issue.py#L610)).
- **A pull request without a root stops the run.** If discovery finds a canonical worker pull request but no recoverable root, the pass fails with `pr_without_recoverable_root`. It does not add the dispatch label or create a second root. A test confirms that no task or label is created ([`test_default_dispatch_does_not_create_root_when_pr_exists_without_ledger`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/tests/test_helmet_issue.py#L5329)).
- **The original clock keeps running.** The checkpoint's `started_at` is set only when it is missing. Budgets are checked before any dispatch mutation, so a resumed run whose repair rounds or issue window are exhausted fails without touching labels or tasks ([`test_budget_before_dispatch_mutation`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/tests/test_helmet_issue.py#L2535)). The default issue window in the tested policy is 8640 minutes, six days ([test](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/tests/test_helmet_issue.py#L2586)). An epic's original start is rechecked on the child's resume and at the merge gate, and an expired managed parent fails closed. These are elapsed windows measured from the original start. They are not a promise of continuous execution.

The same pass classifies where the work stands. A closed issue with a merged pull request becomes `DONE`, including a routed tracking issue closed by hand. A still-open routed issue whose pull request has merged becomes `AWAIT_ACCEPTANCE`. Either way, a hand-closed or already merged issue resolves without new work. A pull request with a new head returns to `REVIEW_HEAD`. An active repair task keeps `WAIT_REPAIR`. An explicit blocked review on an unchanged head stays blocked.

A transferred tracking issue is the case that duplicates work. GitHub gives it a new URL, so the poller sees a new labeled issue and creates a second root unless the Captain runs `helmet adopt-transfer OLD NEW` first. That command re-keys the ledger rows and carries the checkpoint, including `started_at` and repair rounds, to the new URL, but only when the root and latest repair tasks are finished or blocked. A running or queued worker holds instructions naming the old issue, and the documentation says no interface exists to amend or quiesce it. The routing documentation says to remove the dispatch label before the transfer and restore it after adoption. That procedure is documented guidance that this document did not trace through code.

Resuming also needs something to wake the first officer. [`host-continuation.md`](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/skills/helmet-issue/references/host-continuation.md) says to use a native background task that delivers its completion to the first officer, or else one native schedule, five minutes by default. Each wake reconciles once and stays silent when nothing changed. When neither is available, the first officer runs a single pass, records `one_pass_only`, says what is missing, and stops. A process handle that needs repeated output checks is not treated as resumption. After an interruption the first officer adopts a surviving handle or schedule before registering a new one, and it does not restart the worker just to restore observation.

## Where this breaks

The refusals in this loop share one pattern: the pass stops, saves a coded blocker, and does not substitute a guess. An issue with neither label is not dispatched. A pull request that exists without a recoverable root does not get a second root. Conflicting pull request metadata, whether inside one run or between ledger and Kanban, ends the pass. A routed issue that loses its route label resolves to its own repository, and discovery then refuses the foreign pull request instead of adopting it.

The limits below sit outside that pattern:

- **Recording a blocker does not stop a worker.** A checkpoint blocker, a `blocked` review, closing a pull request, or a blocked task changes the first officer's record. It does not cancel a running worker. The delivery guidance says plainly that closing a pull request or recording `blocked` does not cancel its worker, and that the portable issue and transport interface provides no cancellation verb. A blocked repair task still counts as outstanding in the code, so the loop keeps waiting for it.
- **Reclaim is a retry, not a stop.** The supervision guidance offers a same-card `reclaim` for a stuck worker. It tries to terminate the old process on the same host and makes the task runnable again, and the guidance says not to promise the old process has stopped. A comment as corrective direction may not reach a running worker on every deployed version.
- **Replacing a failing approach needs quiescence.** After two failed repairs of one assumption, the guidance says to reassess before another repair-triggering review. A successor is dispatched only after the old attempt is confirmed unable to write. If it cannot be stopped safely, the successor stays undispatched and the exact blocker is reported.
- **Control lives in Hermes Helmet's commands.** The gate protects merges made through `helmet merge`. Nothing in the pinned files stops someone with merge credentials from merging outside it.
- **The reference worker adapter is narrow.** The public `helmet-compose` adapter supports native Kanban and the artifact verbs and refuses the ledger, dispatch and wait verbs. A deployment that wants worker-side adoption through the Captain host supplies its own adapter.

If you want to see this loop on your own project, the [quickstart](https://github.com/MachineWisdomAI/hermes-helmet/blob/5360dcd1637d92c7934cca4ce0c015c5c5befbd2/docs/quickstart.md) walks through writing a policy and sending one issue through Hermes Helmet.
