# Hermes Helmet identities and delegated authority

Hermes Helmet is an open-source software factory from [Machine Wisdom AI](https://machine-wisdom.ai/). It carries an accepted GitHub plan through implementation, review, repair, and authorized merge, with controlled autonomy and Hermes working under its own identity. This Blueprint explains who acts in that process, whose credentials each actor uses, and how Hermes Helmet's controls enforce review and acceptance. It is a retrospective description of the shipped product at source revision [`ec7e238`](https://github.com/MachineWisdomAI/hermes-helmet/tree/ec7e238b45fe0f3a80dfd7f79f8593992eb81902), not a design proposal, and it does not claim the design was approved before or after it was built.

Some rules below are code that refuses to proceed. Some are instructions the bundled first-officer skill gives the coding agent. One field is a consent record that nothing checks at runtime. Each is labelled where it appears.

## Three actors, two sets of credentials

The Captain is you. You agree on a written plan with your coding agent, decide the outcome and scope, and delegate authority to carry the plan through. Your account is the `captain_github_login` in the authority policy.

The first officer is that same coding agent once you have delegated. It runs the bundled skills (`helmet-issue` for a single issue, `helmet-epic` for a graph of issues) inside a coding-agent host such as Codex or Claude Code. It uses the Captain's operating-system account and credentials, and it reviews from a checkout separate from the worker's. It is the Captain's accountable counterpart: responsible for coordinating assignments, explaining the work, reviewing changes, directing repairs, and accepting the result, all within the authority you delegated. It is not a second human who approves every step, and it is not a separate GitHub identity. GitHub records its reviews and merges under the Captain login and records the worker's commits and pull requests under the worker login, so a reader of a pull request can tell which of the two did what.

The crew is Hermes, the Nous Research agent. Hermes runs in Docker with its own GitHub account, the `worker_github_login`, and its own credentials. It implements, tests, opens pull requests, and repairs the same pull request when review finds a problem. It never merges and never force-pushes. Those two rules are stated in the documentation and the generated task text; the code examined does not test what a worker does after it starts.

The two accounts must differ. The worker credential belongs only in the worker runtime, and the Captain host holds only the Captain's profile. Neither side switches profiles, tokens, sessions, or browser state to act as the other or to manufacture an approval.

Two trust categories appear in the policy: trusted humans (GitHub repository roles `OWNER`, `MEMBER`, and `COLLABORATOR`) and trusted bots (exact logins in `trusted_review_bots`). Their reviews can trigger a repair; nobody else's can.

## One policy document

You describe authority in a single JSON file. [Version 2 of the schema](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/docs/authority-schema.md) names the Captain's login, the worker's login, the repositories Hermes may work in, the dispatch and ready labels, the merge mode, and the limits on elapsed time and repair rounds. The schema says validation rejects unknown fields and secret-shaped keys, and that the two logins must differ when compared without regard to case. The ready label must also differ from the dispatch label, so "specified" and "dispatched" cannot collapse into one state. Tokens never go in this file; the schema keeps them in separate owner-only runtime files. Static coverage inspected in [`tests/test_authority.py`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/tests/test_authority.py#L693) targets the rejection of unknown and secret-shaped fields, and [another test](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/tests/test_authority.py#L780) targets the label rule. These tests were read, not run.

Routing is configured here too. An `issue_routes` entry lets a tracking issue in one repository send its code to another, and the schema states that issue text cannot add or widen a route.

Merge authority follows the same pattern. The default mode, `unattended_when_clean`, lets the first officer merge after it has reviewed the exact head and the required checks pass. An issue or epic can narrow that to explicit Captain approval with a whole-line `Merge when clean: no`, which withholds merging until you give separate, explicit approval. If the installation itself sets `explicit_captain_approval`, markers and per-run choices cannot widen it. [`merge_authority_for`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/authority.py#L1347) implements the rule, and [a test](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/tests/test_authority.py#L643) is written to show a manual choice narrowing the default but not widening an explicit-approval policy.

One field is explicitly not a control. `captain_model_provider_consent` records that your delegation includes sending in-scope task and review content to the configured Hermes model. The schema calls it "a consent record used by Captain skills, not a runtime egress gate." The code examined contains no check that stops content from reaching a provider if the first officer ignores the flag.

## Where identity is checked

Identity separation is enforced from both sides, by different code.

On the worker side, [`verify_worker_identity`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/authority.py#L1258) takes the login GitHub reports and fails unless it matches `worker_github_login`. An empty login, the Captain's login, and any other login are each refused with a distinct message. The [issue poller](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/github_issue_poller.py#L253) and the [setup command](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/setup.py#L606) both call it. [`preflight.py`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/preflight.py) wraps it as `check_worker_identity` and `assert_worker_ready`, and both fail closed if the identity probe itself errors. A search of the pinned `src` tree finds no caller of those two wrappers outside their own module, so they are a reusable helper rather than a gate every worker start passes through.

Where several worker role profiles are configured, [`verify_identity` in `worker_role_runtime.py`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/worker_role_runtime.py) runs `gh api user` once per profile, with `GH_TOKEN` and `GITHUB_TOKEN` removed from the environment and the profile's own home directory in place. If the returned login is not the policy's `worker_github_login`, verification raises an error. When the policy names an expected Git credential helper, the check also requires the profile's global Git configuration to list exactly that helper for `https://github.com`.

On the Captain side, the `preflight` function in [`helmet_issue.py`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/helmet_issue.py#L1500) is the gate for a first officer's run. It requires a version 2 policy with both logins set and different, and with valid budgets. It then asks GitHub who is logged in. [`verify_captain_identity`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/authority.py#L1281) refuses the worker's login and anything that is not the Captain. Preflight then lists the credential profiles `gh` stores on that host and refuses to continue if the worker's login is among them. Only after these checks does it load the issue, confirm it is open and carries the ready or dispatch label, and resolve the merge mode. The review-recording, merge, and acceptance commands each repeat the Captain identity and credential-profile checks, so they do not rely on an earlier run.

The pull request is checked as well. A pull request counts only if it sits in the issue's implementation repository and its author is the configured worker (`_validate_worker_pr`). The skill says a pull request authored by anyone else makes the run `FAILED`, and that it must not be adopted or approved. Switching credentials cannot make it acceptable.

## Worker roles are routing, not authority

The worker is not one profile only. An authority policy can add `worker_roles` with three profiles: builder, reviewer, and writing. [`worker_roles.py`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/worker_roles.py) opens with the statement that routing changes assignment, never authority. The builder profile must equal the policy's default assignee. Profile names must be distinct, safe, and not `default`, and the global and per-profile concurrency limits must be positive integers with the per-profile limit no greater than the global one. Malformed configuration raises an error rather than falling back to a default.

An issue goes to the builder unless its body contains a standalone line `Worker role: writing` outside a code fence. The parser accepts exactly one declaration. A duplicate, an unknown value, or a declaration when no roles are configured raises an error, so a mistyped role cannot quietly send work to the wrong profile. Native GitHub review requests select the reviewer role, and a repair keeps the assignment of the task it repairs. The [worker-roles documentation](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/docs/worker-roles.md) says `documentation` and `media` remain accepted aliases for writing under a consolidated policy.

What does not vary is identity. Provisioning gives every role profile the same company contract and the same worker GitHub identity, and verification checks each one. Model choice is independent too: the documentation says model lanes select inference providers while worker roles select assignments. Changing the model Hermes uses does not change who Hermes is on GitHub and does not give it merge authority. Provisioning also refuses to run unless Hermes dispatch is paused and running tasks are drained, so identities and limits cannot change under a task in flight.

## A delegation from plan to merge

The following trace follows the process described in [`docs/captain-and-crew.md`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/docs/captain-and-crew.md). The full flow was not run for this description; the gates it passes through are read from code and identified as such.

You and your coding agent shape the deliverable. The product requirements go into a GitHub parent issue with sub-issues and explicit dependencies, or into one issue for a small change. Creating those issues does not authorize anything. You accept the plan and state the outcome, the scope, and whether merge is authorized. Only then does your agent, now the first officer, start coordinating the accepted work with `helmet-issue` or `helmet-epic`.

Issues carrying the policy's dispatch label are picked up by the poller, which creates one task for the issue. The documentation notes that polling alone does not invoke a model. Hermes takes the task as the worker, opens a tested pull request, and records it as `metadata.published_pr`.

The first officer then reviews the exact head of that pull request as the Captain. Identity separation gives the review its independence: the author is the worker account, the reviewer is the Captain account, and the reviewer works from its own checkout. If review finds a consequential failure, the repair is one dependent task on the same pull request, assigned to the same role as the original, and Hermes reads the review and repairs the existing pull request. Review feedback stays on GitHub; the documentation says Hermes Helmet does not copy review prose into its task board and does not start a repair from a failed check alone. A clean pull request needs no invented repair. The delivery contract says review reports consequential failures and missing acceptance, groups related findings in one pass, and treats small wording or formatting points as nonblocking.

### Exact-head review

A review in Hermes Helmet belongs to a commit. [`effective_captain_review`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/helmet_issue.py#L3015) considers only formal GitHub reviews from the Captain's login whose `commit_id` equals the head being asked about, and takes the latest. Reviews by anyone else, and reviews of earlier commits, do not count. When the first officer records an outcome through [`apply_review_outcome`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/helmet_issue.py#L3245), the code requires that the head SHA it was given is the live head and that GitHub holds a matching formal review: `APPROVED` for a clean result, `CHANGES_REQUESTED` for a repair. Recording "clean" without an approval on that head fails with `formal_review_mismatch`. The skill words this more loosely, saying a clean review may be a comment or an approval "if policy allows"; the code expects `APPROVED`. Review prose is not stored in the checkpoint, because GitHub is the record.

### Merge

By default the first officer merges only when the current head has been reviewed, required checks pass, and the pull request is mergeable. [`merge_issue`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/helmet_issue.py#L3980) takes `--expected-head` (as in `helmet merge ISSUE_URL --expected-head SHA`) and withholds the merge unless the canonical pull request's head equals that value, no repair is pending, and the pull request is not a draft. [`evaluate_merge_gate`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/helmet_issue.py#L2020) then re-reads the pull request and requires the checkpoint's recorded clean head to equal the live head. Its docstring says GitHub's `mergeable_state=clean` is never treated as proof that required checks passed, and that required checks are read from branch rules or classic protection. Unattended merge is allowed only when required checks are verified green. If the policy's `worker_completion_contract` is `local-only` and no required checks are configured, the gate does not grant unattended merge, and explicit Captain approval remains the route. The pull request is read again immediately before merging, and at most one merge request is submitted. A failed or unconfirmed merge is recorded as a blocker and is not retried. The request carries `sha=<head>`, so GitHub itself declines if the branch moved after the last read, and the code then re-queries GitHub to confirm the merge happened.

### Acceptance when work is routed

For same-repository delivery, the merge normally closes the work. Routed work is different. When a tracking issue is routed, the code pull request lives in the implementation repository, and merging it does not finish the tracking issue. [`close_tracking_issue`](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/src/hermes_helmet/helmet_issue.py#L4362), reached through `helmet accept`, is the one place the tracking issue is closed. It refuses an issue that is not routed. The Captain names the merged head, and the function withholds acceptance if that head differs from the pull request's, if the pull request is not merged, or if the checkpoint's clean head does not match. If all three hold, it comments and closes the issue as completed, then reads the issue back and withholds with `tracking_close_unconfirmed` if it is still open. Its docstring says work waiting on the tracking issue unblocks only at that point. Closing out a parent epic remains with the Captain. How the code keeps the tracking issue out of public pull-request text was not examined.

## Where this breaks

The boundary fails closed in the cases the sources name: a missing, Captain-matching, or unexpected worker login; the worker credential found in the Captain's `gh` store (`worker_profile_on_captain_host`); the first-officer path running as the wrong login (`captain_identity_mismatch`); a pull request not authored by the worker; an invalid or duplicated role declaration; and role installation attempted while tasks are running. In each, the response is to stop and report, not to substitute another credential.

### The head moves after review

Suppose the first officer approved head `A`, and the checkpoint holds `A` as the clean head. Before the merge command runs, Hermes pushes a repair, or someone pushes to the branch, so the live head is `B`.

Several checks now disagree with the stale result, and each stops a different step. Recording a Captain review against `A` is refused by `apply_review_outcome` with `review_head_mismatch`, because `A` is no longer the live head. `merge_issue --expected-head A` withholds with `merge_head_mismatch`. If someone passes `B` without having reviewed it, the head check passes, but the checkpoint's clean head is still `A`, so the merge gate returns `head_lacks_clean_captain_review`. A separate check covers a head that changes during the gate itself: the gate re-reads the pull request and returns `merge_gate_head_changed` if the head differs from the one it was handed. Where the checkpoint's clean head matches the live head but the latest Captain review on that commit is no longer `APPROVED`, for example after a later changes-requested review, the gate returns `merge_gate_review_not_approved`. Nothing on this path merges on the strength of the earlier approval.

The static coverage inspected in `tests/test_authority.py` addresses identity, policy, merge-authority rules and the generated review text; it does not cover this sequence. The refusals above are read from the code, not observed running, and the resume path the skill says clears the clean head on a new SHA was not traced.

Recovery is the ordinary loop. The first officer reviews the new head `B` in its own checkout and posts a formal GitHub review as the Captain. It records the outcome with `--record-review` and `--head-sha B`, then runs `helmet merge` with `--expected-head B`. If the review requests changes, the poller turns it into a repair on the same pull request. The skill forbids the first officer from creating a repair task or pushing to the worker's branch. Each distinct changes-requested review spends one repair round, up to the policy limit.

An identity failure recovers differently. Run as the Captain to fix `captain_identity_mismatch`. For `worker_profile_on_captain_host`, the skill says only that the worker credential belongs in the worker runtime, and no command in the examined sources removes it, so correcting it means changing the host's stored credentials yourself. In neither case does the skill allow switching tokens, sessions, or browser state to act as the other identity.

### Limits

The controls live in Hermes Helmet's own commands and in the instructions given to the first officer and the worker. The merge gate protects merges made through `helmet merge`; nothing in the examined sources stops a person or agent who holds merge credentials from merging outside it. The consent record described above is not enforced at runtime. The documentation also describes an audit requirement: every meaningful run should leave evidence of what it read, changed, touched, decided, whether it stayed inside the allowlist, and where the human approved, rejected, or corrected it. The pinned sources include no closeout from an actual run, so that is a stated requirement, not an observed result. These sources describe single-Captain operation; how several Captains or reviewers share one policy is not covered.

If you want to try this on your own project, the [quickstart](https://github.com/MachineWisdomAI/hermes-helmet/blob/ec7e238b45fe0f3a80dfd7f79f8593992eb81902/docs/quickstart.md) walks through writing a policy and sending one issue through Hermes Helmet.
